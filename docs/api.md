# Agenda — API

Every HTTP route, generated by reading `apps/api/main.go`, each module's `router.go`, and
`modules/caldav/handler.go`.

A live Scalar reference is served at `GET /docs`, with the OpenAPI 3.1 document at
`GET /docs/openapi.json` — the same two paths as every other Facile backend. Both are built
by `tronc/apiref` from the per-module `documentation.go` registries, and a test walks the
real router and fails when a route is missing from them. CalDAV is deliberately outside the
spec: it speaks WebDAV verbs OpenAPI cannot express.

## Conventions

- Every JSON endpoint lives under `/api`. Paths outside it are reserved for URLs held
  outside this repo — CalDAV, avatar files, the health probes, and the legacy OIDC
  callback.
- Authenticated routes resolve a token from the `session` cookie first, then the
  `Authorization` header, then a `?token=` query parameter, which is deprecated and logs a
  warning. The token is either a 30-day session token or a user's API token.
- Request and response bodies are JSON, except CalDAV, which is XML and iCalendar.
- Every request body is capped at 4 MB by `middleware.MaxBodySize`.
- Errors come back as JSON from `tronc/httpjson`. `tronc/errors` maps `Invalid` to 400,
  `Unauthorized` to 401, `Conflict` to 409, and `Internal` to 500.

## Service routes

| Method | Path | Auth | Response |
|---|---|---|---|
| GET | `/health` | no | `{"status":"ok"}` — liveness, touches no dependency |
| GET | `/ready` | no | `{"status":"ready"}`, or 503 `{"status":"not_ready"}` if the Postgres ping fails |
| GET | `/api/health` | no | Same handler as `/health` |
| GET | `/api/ready` | no | Same handler as `/ready` |
| GET | `/files/*` | no | Static file server rooted at `STORAGE_DIR`; this is where avatars are served |
| GET | `/auth/oidc/callback` | no | 302 to `/api/auth/oidc/callback`, preserving the query string. Registered only when OIDC is configured |
| GET | `/*` | no | SPA catch-all, gzipped, mounted only when `CLIENT_DIR` contains an `index.html` |

`tronc/health.Mount` registers the probes at both the root and under `/api` so the same
probe answers whether or not the edge proxy forwards only `/api/*`.

## Auth

| Method | Path | Auth | Body | Response |
|---|---|---|---|---|
| GET | `/api/auth/config` | no | — | `{"sso_only": true, "oidc_enabled": bool}`; `sso_only` is always true while an issuer is configured |
| POST | `/api/auth/logout` | no | — | `{"ok":true}`, deletes the session row and clears the cookie |
| GET | `/api/auth/oidc` | no | — | 302 to the provider |
| GET | `/api/auth/oidc/callback` | no | — | 302 to `OIDC_SUCCESS_URL` |
| POST | `/api/auth/sync-profile` | yes | — | Re-pulls name and avatar from the provider |
| GET | `/api/me/invitations` | yes | — | `{"count": n, "href": url}`: pending Registre space invitations for the user menu (`porte/kit` `MountInvitations`). Any failure answers 200 `{"count":0}` without `href`. Cached 60 s per user. Mounted only with `OIDC_ISSUER` |

There is no register or login route: people sign in through Registre only, and
`/api/auth/register` and `/api/auth/login` answer 404. The OIDC routes exist only when
`OIDC_ISSUER` is configured and the provider's discovery document loaded successfully.

The session cookie is `HttpOnly`, `SameSite=Lax`, `Path=/`, with a 30-day `Max-Age`, and
`Secure` whenever the request arrived over TLS or carried `X-Forwarded-Proto: https`.

## Users

All routes require authentication.

| Method | Path | Body | Response |
|---|---|---|---|
| GET | `/api/users` | — | `{"users":[User]}` |
| GET | `/api/users/me` | — | `{"user":User}` |
| GET | `/api/users/{id}` | — | `{"user":User}` |
| PATCH | `/api/users/me` | any of `name`, `email` | `{"user":User}` |
| GET | `/api/users/me/api-token` | — | `{"has_token", "name"?, "created_at"?}` |
| POST | `/api/users/me/api-token` | `{"name"}` | 201 `{"token","name","created_at"}` — the only time the token is returned |
| DELETE | `/api/users/me/api-token` | — | `{"deleted":true}` |

`User` is `{id, email, name, avatar_url, avatar_source, locale, created_at}`. `locale` is
`fr`, `en`, `es` or `de`, taken from the person's Registre profile at each sign-in. `avatar_source` is
`oidc` for a picture pulled from the identity provider.

The API token is the CalDAV password: nobody has an Agenda password, so it is how a person
connects Apple Calendar.

## Spaces

Registre owns shared spaces: their names, members and roles. Agenda follows it and
serves them read-only; create, rename, invite, role changes and leaving happen at
`https://sso.facile.studio/spaces`. Space ids are integers.

| Method | Path | Body | Response |
|---|---|---|---|
| GET | `/api/spaces` | — | `[Space]` — only spaces the caller belongs to |
| GET | `/api/spaces/{spaceID}` | — | `Space` |
| GET | `/api/spaces/{spaceID}/members` | — | `[Member]` |
| POST | `/api/registre/sync` | ignored | 202, no auth — Registre's nudge |

`Space` carries the caller's own `role` alongside `id`, `name`, `description`,
`registre_space_id` (empty until linked), `created_at`, and `updated_at`. `Member` is
`{user_id, email, name, avatar_url, role, joined_at}`.

When OIDC is configured, Agenda imports its existing spaces into Registre once at boot,
retrying with backoff until Registre accepts, and only then starts syncing. It pulls the
full snapshot at boot, every five minutes and two seconds after a nudge, and applies it
in one transaction: spaces link by `registre_space_id`, then by name ignoring case;
members resolve by porte identity, then by email, and are otherwise pre-provisioned so
their first sign-in lands on that account. Members without a Registre identity (local
password accounts) are never removed.

## Calendars

All routes require authentication.

| Method | Path | Body | Response |
|---|---|---|---|
| GET | `/api/calendars` | — | `[Calendar]`; accepts `?space_id=` |
| POST | `/api/calendars` | `{"name","color","description","echo_url","space_id"}` | 201 `Calendar` |
| GET | `/api/calendars/{calendarID}` | — | `Calendar` |
| PUT | `/api/calendars/{calendarID}` | `{"name","color","description","echo_url"}` | `Calendar` |
| DELETE | `/api/calendars/{calendarID}` | — | `{"ok":true}` |
| GET | `/api/calendars/{calendarID}/members` | — | `[Member]` |
| POST | `/api/calendars/{calendarID}/members` | `{"email","role"}` | `{"ok":true}` |
| DELETE | `/api/calendars/{calendarID}/members/{memberID}` | — | `{"ok":true}` |

`Calendar` is `{id, owner_id, name, color, description, echo_url, is_personal, role}`.
`role` is the caller's own access: `owner`, `admin`, `writer`, or `reader`. Sharing is by
email.

## Events

All routes require authentication. Listing and creation are nested under a calendar;
reading, updating, and deleting a single event are not, because an event id is globally
unique.

| Method | Path | Body | Response |
|---|---|---|---|
| GET | `/api/calendars/{calendarID}/events` | — | `[Event]` |
| POST | `/api/calendars/{calendarID}/events` | `CreateEvent` | 201 `Event` |
| GET | `/api/events/{eventID}` | — | `Event` |
| PUT | `/api/events/{eventID}` | `UpdateEvent` | `Event` |
| DELETE | `/api/events/{eventID}` | — | `{"ok":true}` |
| PUT | `/api/events/{eventID}/occurrences/{when}` | `Occurrence` | `Event` |
| DELETE | `/api/events/{eventID}/occurrences/{when}` | — | `Event` |
| POST | `/api/events/{eventID}/occurrences/{when}/restore` | — | `Event` |

The list route takes `from` and `to` query parameters, both RFC 3339 timestamps. An
unparseable value is ignored rather than rejected.

`CreateEvent` is `{title, description, location, start_at, end_at, is_all_day,
recurrence_rule, status, conference_url, conference_provider}`. `UpdateEvent` adds
`calendar_id`: setting it to a different calendar moves the event there, which requires
write access to the target. Both also take `timezone` (IANA name), `color` (`#RRGGBB` or
empty), `attendees` and `reminders`:

- `attendees` is `[{email, name, role, response}]`. `role` is `required` (default) or
  `optional`; `response` is `needs-action` (default), `accepted`, `declined` or
  `tentative`. Agenda stores the invitation and the answer in the event's ICS, so a
  CalDAV client sees them; it sends no mail. Responses add `avatar_url` to an attendee
  whose address is an Agenda account; requests may send it back and it is ignored.
- `reminders` is `[{minutes_before, method}]`, `method` being `display` (default), `audio`
  or `email`, `minutes_before` 0 to 40320. CalDAV clients deliver them.
- On update, an omitted `attendees`, `reminders` or `color` keeps the stored value and an
  empty one clears it. An empty `timezone` keeps the stored zone, so a client that does
  not know the zone cannot re-anchor a recurring series to UTC.
- An unknown `status`, `timezone`, `color`, attendee or reminder is a 400
  `invalid_argument`.

`Event` returns those fields plus `id`, `calendar_id`, `uid`, `etag`, `created_by`
(`{id, name, email, avatar_url}` or null), `created_at`, and `updated_at`. `status` is
`confirmed`, `tentative`, or `cancelled`. It also returns `timezone`, `color`,
`attendees`, `reminders` and `exceptions`, and, in a range-expanded list,
`occurrence_start`.

A recurring event can have single-occurrence exceptions. `{when}` is `YYYY-MM-DD` in the
event's zone, or an RFC 3339 instant when the series recurs more than once a day.
`DELETE` cancels the occurrence (an `EXDATE`), `PUT` overrides it (a `RECURRENCE-ID`
instance) with `Occurrence` `{title, description, location, start_at, end_at, status}`
where every field is optional, and `POST .../restore` removes either. All three return
the series with its `exceptions` list `[{original_start, date, cancelled, title,
start_at, end_at, ...}]`. Expanded lists skip cancelled occurrences and show overrides.
Editing the start, rule, zone or all-day flag of the series discards its exceptions;
any other edit keeps them, as does a CalDAV client's own `EXDATE` and `RECURRENCE-ID`
data.

Every event write bumps `calendars.sync_token`, which is what CalDAV clients poll to
detect changes.

## CalDAV

Not a JSON API. `/dav` is a real CalDAV server backed by
`github.com/emersion/go-webdav/caldav`, speaking `PROPFIND`, `PROPPATCH`, `REPORT`,
`MKCALENDAR`, `GET`, `PUT`, and `DELETE`.

| Path | What it is |
|---|---|
| `/.well-known/caldav` | Discovery. Unauthenticated, 302 to `/dav/` |
| `/dav/{email}` | Principal |
| `/dav/{email}/calendars` | Calendar home set |
| `/dav/{email}/calendars/{calendarID}` | Calendar collection |
| `/dav/{email}/calendars/{calendarID}/{uid}.ics` | Event |

Authentication is HTTP Basic — username is the account email, password is an API token —
or a `session` cookie. A failure answers 401 with
`WWW-Authenticate: Basic realm="Agenda CalDAV"`. The endpoint is rate-limited to 100
requests per minute per client, which is well clear of a typical client's traffic of under
10 per minute.

Configure a client with the server URL `https://agenda.facile.studio/dav/`, your email as
the username, and your API token as the password. Apple Calendar, iOS
Calendar, Thunderbird, and DAVx⁵ are the clients the implementation has been shaped
around; see [architecture.md](architecture.md#caldav) for the compatibility fixes that
made each of them work.
